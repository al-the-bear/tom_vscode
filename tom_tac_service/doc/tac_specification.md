# TAC — Tom Agent Collaboration, protocol specification

| | |
| --- | --- |
| **Protocol version** | `tac/1.0` |
| **Store format version** | `formatVersion: 1` |
| **Status** | internal draft: the reference the coordination service, its client and the GitHub backend are built and tested against. It is published once it works for us. |
| **Owner** | the quest agent_coordination (until it exists: vscode_extension) |

TAC defines the records every coordination backend keeps and the operations
every backend offers, with the same meaning on each. A runtime (a VS Code
window's runtime, Webforge, a runtime server) talks TAC through one client to
whichever backend its workspace names:

- **the local service:** one per machine and OS user, started by the first
  runtime that needs it;
- **the server:** the same service, long-running, reached over the network,
  with customers, keys and quotas;
- **the GitHub backend:** the records as refs in a coordination repository,
  written through GitHub's REST API by each runtime's client.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Scope

TAC covers:

- the **records** (§ 3): customers, agent groups, runtimes, sessions,
  resources, units, leases with fencing tokens, messages, endpoints, quotas;
- the **lease lifecycle** (§ 4);
- the **operations** (§ 5) and what each backend leaves out (§ 6);
- the **error codes** (§ 7) and **versioning** (§ 8);
- two **bindings**: HTTP and WebSocket for the services (§ 9), refs in a
  repository for the GitHub backend (§ 10).

TAC does not interpret message types or payloads, nor endpoint types,
protocols or `meta`: those are conventions between the clients. A backend
stores, routes and returns them unchanged.

## 2. Conventions

- **Wire format:** JSON (RFC 8259), UTF-8. A YAML rendering of a payload is
  only how a client shows it.
- **Times:** strings in UTC ISO 8601 with a `Z` suffix and millisecond
  precision, e.g. `2026-11-14T13:05:00.000Z`. Every time in a record is
  assigned by the **backend's clock**, never by a client (§ 4.4).
- **Ids:**
  - `messageId`, `leaseId` and `runtimeId` are ULIDs (26 characters, Crockford
    base32, sortable by creation time);
  - `runtimeId` is generated by the runtime when its process starts, and is
    new on every start;
  - `leaseId` and `messageId` are generated by the backend;
  - `endpointId` is `<runtimeId>/<type>/<n>` (§ 3.10);
  - `groupId` and `customerId` match `^[a-z0-9][a-z0-9_-]{0,62}$`.
- **Unknown fields:** a reader MUST ignore fields it does not know, and a
  backend MUST keep them when it rewrites a record (§ 8).
- **Every record** carries `protocolVersion` (the version of the writer, e.g.
  `tac/1.0`) when it is stored; on the wire it MAY be left out of nested
  records.
- **Request ids:** `acquire`, `send` and `publish` carry a client-generated
  `requestId` (a ULID). A backend MUST answer a repeated request with the same
  `requestId` in the same group with the result of the first one, for at least
  24 hours, so a client can retry after a lost answer without doing the work
  twice.

## 3. Records

### 3.1 Customer

| Field | Type | Meaning |
| --- | --- | --- |
| `customerId` | string | the customer's id |
| `name` | string | display name |
| `quotas` | Quota | the limits (§ 3.12) |

Access keys are created for a customer and checked against it. Customers exist
on the server only; the local service and the GitHub backend have the one
implicit customer named in the group's settings.

### 3.2 Agent group

The runtimes that coordinate with each other: they share one backend and its
settings.

| Field | Type | Meaning |
| --- | --- | --- |
| `groupId` | string | the group's id, unique on its backend |
| `customerId` | string | the customer that owns it |
| `mode` | `local` / `github` / `server` | its backend kind; it changes only by a migration (§ 5.8) |
| `settings` | GroupSettings | below |
| `units` | Unit[] | the repository units (§ 3.7) |
| `infra` | InfraResource[] | the declared infrastructure resources (§ 3.6) |
| `createdAt` | time | |
| `migratedTo` | BackendIdentity, optional | set on the old backend once the group moved (§ 5.8) |

`GroupSettings`:

| Field | Type | Meaning |
| --- | --- | --- |
| `branchGranularity` | `none` / `item` / `group` | whether and how claims get todo branches and worktrees |
| `autoUpdate` | boolean | the opt-in for the auto-update of unclaimed repositories |
| `extra` | object | further settings, kept unchanged |

`BackendIdentity`: `{mode, repository?, serverUrl?, groupId}` — `repository`
(`<owner>/<repo>`) for `github`, `serverUrl` for `server`.

Which runtimes form a group: every runtime whose workspace configuration names
the same backend and group id. The local service holds one group per backend
setting of its machine.

### 3.3 Runtime

One process serving one workspace root: a VS Code window's runtime, Webforge,
a runtime server.

| Field | Type | Meaning |
| --- | --- | --- |
| `runtimeId` | ULID | generated by the runtime at process start |
| `groupId` | string | |
| `kind` | `vscode` / `webforge` / `runtime-server` | |
| `host` | string | the machine's name |
| `workspace` | string | the workspace's name in its `agent.workspace.yaml` |
| `workspaceRoot` | string | absolute path on `host` |
| `quests` | string[] | the quests it serves; empty when `hasQuest` is false |
| `hasQuest` | boolean | false for a runtime that serves no quest (e.g. Webforge's webwork runtime, workspace `webwork-app`) |
| `clones` | Clone[] | the coordinated repositories on this host |
| `backend` | BackendIdentity | the backend the runtime is configured for (for the misconfiguration check, § 6.4) |
| `repositories` | string[] | the repository identities its `agent.workspace.yaml` lists |
| `status` | RuntimeStatus | its current state, below |
| `registeredAt` | time | |
| `presenceRenewedAt` | time | |
| `present` | boolean | computed by the backend from presence (§ 5.2), never written by a client |

`Clone`: `{repository, path, head, behind, ahead, dirty}` — `repository` the
identity (`<provider>/<owner>/<repo>`), `head` the commit, `behind` / `ahead`
counts against its upstream, `dirty` whether the working tree has changes.

`RuntimeStatus`: the state the runtime's notifications change, so a client
that connects late still shows the right counts:

| Field | Type | Meaning |
| --- | --- | --- |
| `process` | object, optional | per quest and run: process, phase, step, substep, iterations, completed |
| `openQuestions` | integer | blocking asks waiting for the user |
| `openItems` | integer | queue items needing attention |
| `openReviews` | integer | reviews waiting for the user |
| `queue` | `idle` / `sending` / `paused` / `stopped` | |

One quest MAY have several runtimes.

### 3.4 Session

The identity a lease belongs to. It outlives a window reload: the same session
key on a new runtime re-attaches to its lease.

| Field | Type | Meaning |
| --- | --- | --- |
| `sessionKey` | SessionKey | below |
| `runtimeId` | ULID | the runtime serving it now |
| `lastActivity` | time | |
| `currentItem` | `{itemId, todoId?}`, optional | what it works on |
| `openedAt` | time | |

`SessionKey` is `{quest, session, run, host, workspace}`. Its text form, used
in paths and as a map key, is

```text
<quest>#<session>@<run>/<host>/<workspace>
```

with each part percent-encoded (RFC 3986 unreserved characters kept), so the
separators `#`, `@` and `/` never occur inside a part. Example:
`vscode_extension#idea@collab/mbp/tom_agent_container`.

### 3.5 Resource key

A string naming what a lease holds:

| Form | Example | Covers |
| --- | --- | --- |
| `<provider>/<owner>/<repo>` | `github/al-the-bear/tom_vscode` | the whole repository |
| `<provider>/<owner>/<repo>:<unit path>` | `github/al-the-bear/tom_vscode:tom_vscode_extension/src/managers` | one unit of it (§ 3.7) |
| `infra:<name>` | `infra:vsix-release` | a declared infrastructure resource |
| `ai:<path>` | `ai:quests/vscode_extension` | a folder of the `_ai` state |

Repositories are named by identity, never by a path on a machine. Unit paths
use `/`, are relative to the repository root and carry no leading or trailing
`/`.

**Conflicts.** Two keys conflict when:

- both name the same repository and one is the whole repository; or
- both name units of the same repository and one unit path is the other or a
  path prefix of it at a `/` boundary;
- both are the same `infra:` key, or the same `ai:` key.

A path listed in a unit's `shared` conflicts with nothing. Keys conflict only
within one group.

### 3.6 Infrastructure resource

`{name, description}`, declared in the group's data. `infra:<name>` keys MAY
only name declared resources; an undeclared one is `invalid`.

### 3.7 Unit

| Field | Type | Meaning |
| --- | --- | --- |
| `repository` | string | the repository identity |
| `path` | string | the unit's path in it |
| `shared` | string[] | paths under `path` any holder may write; they conflict with nothing |
| `description` | string, optional | |

Units are kept in the backend's data and copied by a migration.

### 3.8 Lease and fencing token

One lease per session, listing all its resources; renewing it renews them all.

| Field | Type | Meaning |
| --- | --- | --- |
| `leaseId` | ULID | |
| `groupId` | string | |
| `sessionKey` | SessionKey | |
| `resources` | LeaseResource[] | below |
| `acquiredAt` | time | |
| `renewedAt` | time | |
| `expiresAt` | time | `renewedAt` + 60 minutes |
| `state` | `active` / `stale` / `freed` / `released` | § 4 |
| `freedAt`, `freedBy` | time, string, optional | set by `free` |

`LeaseResource`:

| Field | Type | Meaning |
| --- | --- | --- |
| `key` | resource key | |
| `token` | integer | the fencing token granted with it |
| `acquiredAt` | time | |
| `hold` | `item` / `group` | `group` when a todo group holds it from its first to its last todo |
| `branch` | string, optional | the todo branch the claim works on |
| `worktree` | string, optional | the worktree path on the holder's host |

**The fencing token** is kept per resource key, not per lease, because a merge
check asks about one resource: "is this token still the current one for this
repository?". Per key the backend keeps `nextToken`, a positive integer that
only grows:

- every grant of the key takes `token = nextToken` and raises `nextToken` by 1;
- every `free` of a lease raises `nextToken` of each of its keys by 1.

A token is **current** while a lease in state `active` or `stale` holds the key
with that token. A released or freed claim's token is never current again, and
since `nextToken` only grows, it never becomes current by accident.

### 3.9 Message

| Field | Type | Meaning |
| --- | --- | --- |
| `messageId` | ULID | assigned by the backend |
| `class` | `notification` / `command` | |
| `type` | string | free; the backend never reads it |
| `origin` | `{sessionKey?, quest, run?, host, runtimeId}` | who sent it |
| `targets` | `"all"` or string[] | quests; commands MUST name quests, not `all` |
| `preferHost` | string, optional | commands: the host whose runtime should take it (§ 5.6) |
| `payload` | object | free; the backend never reads it; its serialized size is limited by `maxPayloadBytes` |
| `createdAt` | time | |
| `deliveries` | Delivery[] | commands only, one per target quest |

`Delivery`:

| Field | Type | Meaning |
| --- | --- | --- |
| `quest` | string | the target |
| `state` | `pending` / `delivered` / `acknowledged` / `expired` | |
| `deliveredTo` | ULID[] | runtimes it was pushed to |
| `acknowledgedBy` | ULID, optional | the runtime that took it |
| `outcome` | `taken` / `refused` / `filed`, optional | with `acknowledged` |
| `reason` | string, optional | with `refused` |
| `expiresAt` | time | `createdAt` (or the last `resend`) + 7 days |

**Notifications** are live only: the backend pushes them to the runtimes
connected at the time and stores nothing. **Commands** are stored and forwarded
as well as possible, with a delivery state per target.

### 3.10 Endpoint

A network endpoint a runtime serves, so the group's other runtimes and clients
can find it. The registry says only where it is; the endpoint checks who may
use it.

| Field | Type | Meaning |
| --- | --- | --- |
| `endpointId` | string | `<runtimeId>/<type>/<n>`, `n` counting this runtime's endpoints of that type from 1 |
| `type` | string | free; the first are `remote-control` and `mcp` |
| `url` | string | the endpoint's address, with its transport as scheme, e.g. `tcp+jsonrpc://127.0.0.1:19930`, `http://10.8.0.7:19920/` |
| `scope` | `loopback` / `vpn` / `public` | where `url` is reachable from |
| `quest`, `host`, `runtimeId` | string | whose endpoint it is |
| `protocol` | string | the protocol and its version, e.g. `tom-runtime/1` |
| `auth` | `{kind: "none"}` or `{kind: "bearer", keyEnv}` | how to authenticate; never a secret |
| `meta` | object | free key–value pairs |
| `publishedAt` | time | |

An endpoint exists only while its runtime is present (§ 5.2): when presence
ends, the backend withdraws it.

### 3.11 Group export

What `migrate` carries from one backend to another (§ 5.8):
`{formatVersion, group (§ 3.2, with units and infra), tokens: {<key>:
nextToken}, commands: Message[] (undelivered), runtimes: Runtime[] (for the
record)}`.

### 3.12 Quota

Per customer, enforced by the server; the local service has none, and the
GitHub backend's limit is GitHub's own.

| Field | Kind | Counts |
| --- | --- | --- |
| `maxGroups` | held | groups of the customer |
| `maxRuntimes` | held | registered runtimes per group |
| `maxResourcesPerLease` | held | resources in one lease |
| `maxActiveLeases` | held | leases in `active` or `stale` per group |
| `callsPerHour` | rate | requests per sliding hour |
| `messagesPerHour` | rate | messages sent per sliding hour |
| `maxPayloadBytes` | size | a message payload, serialized |
| `maxStoredCommands` | held | stored, unacknowledged commands per group |

Rates are counted over a sliding hour and persisted, so a restart does not
reset them; held limits are checked when something is added. A quota MUST NOT
block `release`, `deregister`, `closeSession`, `ack`, `withdraw`, nor `renew` of
a lease already held.

## 4. The lease lifecycle

### 4.1 States and transitions

| From | Event | To | Who |
| --- | --- | --- | --- |
| — | `acquire` of a session's resources, all granted | `active` | the queue, before an item is sent |
| `active` | `acquire` of more resources by the same session | `active`, resources added | the queue |
| `stale` | `acquire` of more resources by the same session | `active`, renewed, resources added | the queue, the holder coming back |
| `active` | `renew` | `active`, `renewedAt` / `expiresAt` moved on | the client, while the session works |
| `active` | `expiresAt` passes | `stale` | the backend's clock |
| `stale` | `renew` by its own session | `active` | the holder, before anybody freed it |
| `active` / `stale` | `free` | `freed`; every key's `nextToken` grows | the user |
| `active` / `stale` | `release` of all its resources | `released` | the queue |
| `active` / `stale` | `release` of some resources | unchanged, those removed | the queue |

`freed` and `released` are final. A session that acquires again after them
gets a new lease.

### 4.2 Rules

- **Stale is only shown, never acted on by a machine.** No backend and no
  client takes a stale lease over; only the user frees it. A stale lease's
  resources stay held, and their tokens stay current.
- **A freed holder finds out** at its next pre-flight: its tokens are no
  longer current (`checkToken` answers `false`). A merge it still attempts is
  refused by the same check.
- **Renewal timing:** a backend accepts a `renew` at any time. A client SHOULD
  renew between minute 45 and minute 59 after the last renewal (aiming at
  minute 50), which keeps within the GitHub budget and leaves several
  attempts before the lease goes stale.
- **Staleness is evaluated lazily:** a backend MAY store `active` and answer
  `stale` whenever `expiresAt` lies in the past at the time of the read.

### 4.3 A window reload

The session key stays the same, so the new runtime process re-attaches to its
lease: it calls `openSession` with the same key and its new `runtimeId`, and
`listLeases` answers the lease with its tokens unchanged.

### 4.4 Clocks

`acquiredAt`, `renewedAt`, `expiresAt`, `presenceRenewedAt` and staleness use
the backend's clock: the service's own, or on GitHub the server-assigned commit
dates of the refs (§ 10). A machine whose clock is off can neither make a lease
look fresh nor make one go stale early.

## 5. Operations

Each operation answers a result or an error (§ 7). Every operation except
`hello` and the admin operations names its group. Operations a backend does not
offer answer `unsupported` and are absent from its `capabilities` (§ 6).

### 5.1 Handshake

**`hello(protocolVersion, client, groupId?, settings?)`**

- In: `protocolVersion` (e.g. `tac/1.0`); `client` `{name, version}`;
  optionally the `groupId` the client works in and, for a group not yet known,
  its `settings`, `customerId` and `mode`.
- Out: `{protocolVersion, formatVersion, capabilities, customer?, groups,
  group?, migratedTo?}` — `capabilities` the areas offered (`runtimes`,
  `sessions`, `leases`, `units`, `messages`, `endpoints`, `migrate`),
  `groups` the ids the caller may use, `group` the named group's record.
- Errors: `versionMismatch` when the major versions differ (`details`: both
  versions and what to update); `migrated` when the group moved (`details`:
  `migratedTo`).
- Creating a group: on the local service a `hello` naming an unknown group
  with its settings creates it; on the GitHub backend the first `hello` creates
  `refs/tac/meta`; on the server groups are created by the admin API, and an
  unknown group answers `notFound`.

### 5.2 Runtimes and presence

| Operation | In | Out |
| --- | --- | --- |
| `register(runtime)` | the Runtime record without the backend's fields | the stored record |
| `renewPresence(runtimeId, clones?, status?)` | changed fields | the stored record |
| `deregister(runtimeId)` | | nothing |
| `listRuntimes(filter?)` | `quest`, `host`, `presentOnly` | Runtime[] |

- `register` with a `runtimeId` that already exists replaces its record (a
  retry).
- **Presence on the services:** a runtime is present while its message stream
  (`subscribe`) is open, and for 2 minutes after it closed; `renewPresence`
  also refreshes `presenceRenewedAt` and counts as presence for 2 minutes.
- **Presence on GitHub:** a runtime is present while `presenceRenewedAt` is at
  most 60 minutes old; it renews with its sessions' lease renewals, at least
  once an hour, with no calls of its own.
- When presence ends, the backend withdraws the runtime's endpoints. Its
  leases stay and go stale on their own clock.

### 5.3 Sessions

| Operation | In | Out |
| --- | --- | --- |
| `openSession(sessionKey, runtimeId)` | | the Session; re-attaches an existing one to the new runtime |
| `touchSession(sessionKey, currentItem?)` | | the Session with `lastActivity` updated |
| `closeSession(sessionKey)` | | nothing; its lease, if any, stays until released |
| `listSessions(filter?)` | `quest`, `host`, `runtimeId` | Session[] |

On GitHub `touchSession` rides along with the next renewal and costs no call of
its own.

### 5.4 Leases

**`acquire(sessionKey, resources, hold, requestId)`**

- In: `resources` a non-empty list of resource keys, `hold` `item` or `group`,
  optionally per key `branch` / `worktree`.
- Out on success: `{granted: true, lease}` with a new token per granted key.
- Out on conflict: error `conflict` with `details.holders`, per refused key:
  `{key, sessionKey, leaseId, state, since}` — so a waiting item can name the
  holder and say whether it is stale.
- **All or none, race-free:** either every key is granted or none is, and
  concurrent acquires of overlapping sets cannot both succeed. Keys already
  held by the same session's lease are granted again without a new token.
  Keys are processed in sorted order, so two sessions after overlapping sets
  cannot deadlock.
- Errors besides `conflict`: `quotaExceeded` (`maxResourcesPerLease`,
  `maxActiveLeases`), `invalid` (an unknown `infra:` name, a malformed key).

| Operation | In | Out | Errors |
| --- | --- | --- | --- |
| `renew(leaseId, sessionKey)` | | the Lease | `notHolder` when the lease is freed or released, or is another session's |
| `release(leaseId, sessionKey, resources?)` | all when omitted | the Lease | `notHolder` |
| `free(leaseId, by)` | the user's action; `by` names who | the Lease, `freed` | `notFound`; freeing a released or freed lease is a no-op |
| `listLeases(filter?)` | `sessionKey`, `key`, `states` | Lease[], with `state` evaluated now | |
| `checkToken(key, token)` | | `{current: boolean, holder?}` | |

`release` of a key the lease does not hold is ignored. `free` MAY be applied to
several leases at once by the client (e.g. everything of one host).

### 5.5 Units and infrastructure resources

| Operation | In | Out |
| --- | --- | --- |
| `listUnits()` | | `{units, infra}` |
| `setUnits(units, infra?)` | the whole lists | the stored lists |

`setUnits` replaces the lists. Changing units does not touch existing leases;
it changes which keys conflict from then on.

### 5.6 Messages

| Operation | In | Out |
| --- | --- | --- |
| `send(message, requestId)` | `class`, `type`, `origin`, `targets`, `preferHost?`, `payload` | `{messageId, createdAt}` |
| `subscribe(runtimeId)` | | a stream of notifications and commands for the runtime's quests and `all` |
| `pendingCommands(runtimeId)` | | the commands for its quests not yet acknowledged |
| `ack(messageId, runtimeId, outcome, reason?)` | `outcome` `taken` / `refused` / `filed` | `{acknowledged: boolean, by}` |
| `listUndelivered(filter?)` | `quest`, `states` | commands with a delivery not `acknowledged` |
| `resend(messageId, quest?)` | | the message, its expired or refused deliveries back to `pending` with a new `expiresAt` |
| `drop(messageId)` | | nothing; the command is removed |

- **Routing:** a notification goes to every connected runtime of the group
  whose `quests` meet `targets` (every runtime for `all`). A command goes,
  per target quest, to every present runtime serving that quest; with
  `preferHost`, to the runtimes on that host only, as long as one of them is
  present.
- **One runtime takes a command:** per target, the first `ack` wins and
  answers `acknowledged: true`; a later `ack` for the same target answers
  `acknowledged: false` with `by`, and those runtimes show it as taken.
- **`outcome`:** `taken` — the runtime carries it out (for our clients: it is
  queued); `refused` — it cannot, with `reason`; `filed` — a client filed it
  into the target quest's inbox or todo list for a quest with no runtime.
- **Expiry:** a delivery still `pending` or `delivered` at its `expiresAt`
  (7 days) becomes `expired` and stays listed until resent or dropped.
- **After a reconnect** a runtime asks for the current state (`listRuntimes`,
  `listLeases`, its `pendingCommands`); notifications are never replayed.
- `send` with a payload over `maxPayloadBytes` answers `invalid`, or
  `quotaExceeded` on the server.

### 5.7 Endpoints

| Operation | In | Out |
| --- | --- | --- |
| `publish(endpoint, requestId)` | the Endpoint without `endpointId` / `publishedAt` | the stored Endpoint |
| `withdraw(endpointId)` | | nothing |
| `listEndpoints(filter?)` | `type`, `quest`, `host` | the endpoints of present runtimes |

A runtime publishes an endpoint after its server listens, with the port it
actually bound, and withdraws it before it stops.

### 5.8 Migration

**`migrate(toMode)`** moves a group from one backend to another. TAC defines
its two halves; the client runs the steps around them (exclusive access to
every repository, rewriting the workspaces' configuration, releasing).

- **`export()`** on the old backend answers the Group export (§ 3.11) and marks
  nothing.
- **`import(export)`** on the new backend creates the group with its settings,
  units and infra, sets each key's `nextToken` to the exported value (so tokens
  keep growing and an old token can never look current there) and stores the
  undelivered commands. A backend that already holds the group id answers
  `conflict`.
- **`markMigrated(migratedTo)`** on the old backend sets `migratedTo`. From then
  on `hello` for the group answers `migrated`.

Every step is idempotent, so a failed migration can be finished by running the
steps again.

## 6. Backends

### 6.1 What each offers

| Area | Local service | Server | GitHub backend |
| --- | --- | --- | --- |
| Handshake | yes | yes | yes, from `refs/tac/meta` |
| Runtimes, presence | yes, presence by stream | yes, presence by stream | yes, presence renewed with the lease renewals (at least hourly) |
| Sessions | yes | yes | yes; `touchSession` rides along with a renewal |
| Leases | yes | yes | yes |
| Units | yes | yes | yes |
| Messages | yes | yes | **no**: `unsupported`; a GitHub group's runtimes send messages through their machine's local service, so they reach the runtimes of that machine only |
| Endpoints | yes | yes | yes, in the runtime refs |
| Migration | yes | yes | yes, as source and target |
| Customers, keys, quotas | no (one OS user, a key file) | yes (admin API) | no (GitHub's own limits) |

A client routes an area its backend does not offer elsewhere: a GitHub group's
messages to the local service.

### 6.2 How acquire stays all-or-none

- **Services:** one store transaction per `acquire`.
- **GitHub:** one compare-and-swap ref per resource (§ 10), written in sorted
  key order; on the first refusal the refs already written are released again
  in reverse order and the call answers `conflict`. A lost compare-and-swap is
  re-read and retried at most 5 times with jitter; after that the client
  answers `busy` (§ 7) and retries later.

### 6.3 The GitHub budget

The GitHub backend runs in each runtime's client, so the client counts its own
calls (the rate-limit headers, and its own sliding counters of content-creating
calls per minute and per hour). Renewals and releases always go out; acquires
wait when the budget is spent; a `403` or `429` with `retry-after` stops every
call of that machine until then. The budget is a client concern, not a TAC
error: a spent budget answers `busy` with `retryAfter` to the caller.

### 6.4 The misconfiguration check

Every runtime registers with its machine's local service, whatever its own
mode, reporting `backend` and `repositories` (§ 3.3). The local service
compares the registrations of the machine (present or seen in the last 7 days)
and reports, as `warnings` in its `listRuntimes` answer:

- one repository identity under two different backend identities;
- two workspaces naming the same group id with different backends;
- a listed repository whose clone is missing or whose `origin` does not match.

A warning blocks nothing.

## 7. Errors

An error is `{code, message, details?}`. `message` is a sentence for a person;
clients act on `code`.

| Code | Meaning | `details` | HTTP |
| --- | --- | --- | --- |
| `conflict` | a resource is held by another session; or an import finds the group id taken | `holders` (§ 5.4) | 409 |
| `staleToken` | a token is not current where a current one is required | `key`, `token`, `current?` | 412 |
| `notHolder` | the lease is not (or no longer) the caller's session's | `leaseId`, `state` | 403 |
| `quotaExceeded` | a quota is reached | `quota`, `limit`, `current`, `retryAfter` (seconds) | 429, with `Retry-After` |
| `versionMismatch` | the protocol's major versions differ | `client`, `backend`, `update` | 426 |
| `unsupported` | the backend does not offer the area | `area` | 501 |
| `migrated` | the group moved to another backend | `migratedTo` | 410 |
| `notFound` | the group, lease, message or endpoint does not exist, or belongs to another customer | `what` | 404 |
| `invalid` | the request does not match the schema | `errors` | 400 |
| `unauthorized` | no key, a wrong key, or a key not valid for the group | | 401 |
| `unavailable` | the backend cannot write (disk full, store not writable); reads still work | `reason` | 503 |
| `unreachable` | **client only:** the backend could not be reached after the client's retries | `cause` | — |
| `busy` | **client only:** the GitHub backend lost its retries, or its budget is spent | `retryAfter?` | — |

`unreachable` starts the client's outage behaviour (the group's queues stop
after their current item). `unauthorized` for another customer's group is
answered as `notFound`, so the group's existence is not revealed.

## 8. Versioning

- **The protocol version** is `tac/<major>.<minor>`, starting at `tac/1.0`.
  - A **minor** version only adds: optional fields, operations, error codes,
    capabilities. Every reader ignores what it does not know and keeps unknown
    fields when it rewrites a record. A client MUST treat an unknown error code
    like a failed request with that `message`.
  - A **major** version changes or removes something. `hello` refuses a client
    whose major version differs with `versionMismatch`.
- **The stored data** (a service's store, a coordination repository) carries a
  `formatVersion` of its own, starting at `1`. It is raised only when a change
  is not backwards compatible, never routinely, and raising it is a migration.
  A backend that finds a newer `formatVersion` than it knows refuses to start
  (a service) or answers `unavailable` (the GitHub backend), naming the version
  it needs.
- **This document** states both numbers in its header and changes with them.

## 9. Binding: HTTP and WebSocket (local service, server)

### 9.1 Requests

- HTTP/1.1 with JSON bodies, under `/tac/<major>/`; for this version
  `/tac/1/`.
- Authentication: `Authorization: Bearer <key>` on every request and on the
  WebSocket upgrade. The local service's key is the content of
  `~/.tom/coordination/local.key` (mode 0600); the server's keys are created by
  its admin API and stored only as salted hashes.
- Every request MAY carry `Tac-Protocol-Version: tac/1.0`; a service answers
  `versionMismatch` for a different major version.
- The local service listens on `127.0.0.1:19890` (configurable).

### 9.2 Paths

`{g}` is `/tac/1/groups/{groupId}`; path parameters are percent-encoded
(a session key's text form, § 3.4; a resource key in `tokens/{key}`).

| Method and path | Operation |
| --- | --- |
| `GET /tac/1/hello?protocolVersion=…&client=…&groupId=…` (settings, when given, as `POST /tac/1/hello` with a body) | `hello` |
| `POST {g}/runtimes` · `PUT {g}/runtimes/{runtimeId}/presence` · `DELETE {g}/runtimes/{runtimeId}` · `GET {g}/runtimes` | `register`, `renewPresence`, `deregister`, `listRuntimes` |
| `POST {g}/sessions` · `PATCH {g}/sessions/{sessionKey}` · `DELETE {g}/sessions/{sessionKey}` · `GET {g}/sessions` | `openSession`, `touchSession`, `closeSession`, `listSessions` |
| `POST {g}/leases` · `POST {g}/leases/{leaseId}/renew` · `POST {g}/leases/{leaseId}/release` · `POST {g}/leases/{leaseId}/free` · `GET {g}/leases` · `GET {g}/tokens/{resourceKey}?token=…` | `acquire`, `renew`, `release`, `free`, `listLeases`, `checkToken` |
| `GET {g}/units` · `PUT {g}/units` | `listUnits`, `setUnits` |
| `POST {g}/messages` · `GET {g}/runtimes/{runtimeId}/commands` · `POST {g}/messages/{messageId}/ack` · `GET {g}/messages/undelivered` · `POST {g}/messages/{messageId}/resend` · `DELETE {g}/messages/{messageId}` | `send`, `pendingCommands`, `ack`, `listUndelivered`, `resend`, `drop` |
| `POST {g}/endpoints` · `DELETE {g}/endpoints/{endpointId}` · `GET {g}/endpoints` | `publish`, `withdraw`, `listEndpoints` |
| `POST {g}/migrate/export` · `POST /tac/1/groups` · `POST {g}/migrate/mark` | `export`, `import`, `markMigrated` |
| `WS {g}/stream?runtimeId=…` | `subscribe` |
| `/tac/1/admin/…` (server only) | customers, keys, groups, quotas |
| `POST /tac/1/admin/handover` (local service) | asks an older service to stop for a newer one |

Filters are query parameters. Results are the records of § 3 as JSON; lists are
`{items: [...]}`.

### 9.3 The stream

- Frames are JSON text messages: from the service `{kind: "notification" |
  "command", message}`, from the runtime `{kind: "ack", messageId, outcome,
  reason?}` (equivalent to `ack`).
- Both sides ping every 30 seconds; a peer silent for 90 seconds is
  disconnected.
- The open stream is the runtime's presence (§ 5.2). On connect the service
  pushes the runtime's pending commands once.

### 9.4 Errors

The body of an error answer is the error object of § 7, with its HTTP status.
A request the service did not finish (it crashed or the connection dropped) is
retried by the client with the same `requestId`.

## 10. Binding: refs in a coordination repository (GitHub backend)

One private repository per group. No branches and no files on branches: every
record is a ref pointing to a standalone commit whose tree holds one JSON file.
A write is three calls (a tree with the file inline, a commit whose parent is
the ref's current commit, and creating or moving the ref without `force`), so
every move is a compare-and-swap.

| Ref | File | Holds | Written by |
| --- | --- | --- | --- |
| `refs/tac/meta` | `group.json` | `formatVersion`, `protocolVersion`, the Group record (§ 3.2) with units and infra | `hello` (creation), `setUnits`, migration |
| `refs/tac/repos/<key>` | `claims.json` | `nextToken`, and the claims on this repository: unit path or whole, `sessionKey`, `leaseId`, `token`, `hold`, `branch`, `worktree`, `acquiredAt` | `acquire`, `release`, `free` |
| `refs/tac/infra/<name>`, `refs/tac/ai/<path>` | `claims.json` | the same, for `infra:` and `ai:` keys | the same |
| `refs/tac/sessions/<session>` | `session.json` | the Session record, its `leaseId`, the keys it holds, `currentItem` | `openSession`, `renew`, `closeSession` |
| `refs/tac/runtimes/<runtimeId>` | `runtime.json` | the Runtime record and the endpoints it publishes | `register`, `renewPresence` (with renewals), `publish`, `withdraw` |

- **One ref per repository, not per claim:** units of one repository are claims
  in one `claims.json`, so a unit and its parent can never be granted to two
  sessions: both writes go through the same compare-and-swap.
- **Names:** `<key>` is the resource key with `/` and `:` written as `~`
  (`github~al-the-bear~tom_vscode`); `<session>` is
  `<quest>~<session>~<run>~<host>~<workspace>`; characters git does not allow
  in a ref name are written `~xx` (two hex digits).
- **Times:** `renewedAt` of a lease and `presenceRenewedAt` of a runtime are the
  committer dates GitHub assigns to the commits of the session and runtime
  refs. A lease's staleness is computed from its session ref's last commit.
- **A lease in the refs** is the session ref (state, renewal) together with its
  claims in the resource refs. `free` removes the claims from the resource
  refs, raises their `nextToken` and marks the session ref `freed`.
- **History:** each ref keeps its chain of small commits; cutting the chains is
  a maintenance step with exclusive access, started by the user.

## 11. Points this specification fixes

The design these choices complete left them open; they are fixed here and can
be changed before the specification is published:

1. `runtimeId` is generated by the runtime (a ULID per process start); `leaseId`
   and `messageId` by the backend.
2. A session key's text form is `<quest>#<session>@<run>/<host>/<workspace>`,
   each part percent-encoded.
3. A group is created by the first `hello` naming it on the local service and
   on GitHub, and by the admin API on the server.
4. `acquire` by a session whose lease is stale renews it and adds the
   resources; `freed` and `released` are final.
5. A token is current while its lease is `active` or `stale`.
6. Commands name quests, never `all`; `preferHost` limits delivery to that
   host while one of its runtimes is present.
7. `ack` carries an outcome (`taken`, `refused`, `filed`); `filed` covers a
   command a client filed into the inbox of a quest with no runtime.
8. Request ids are remembered for 24 hours; `publish` carries one too.
9. Error codes beyond the design's: `migrated` (410), `notFound` (404),
   `invalid` (400), `unauthorized` (401), `unavailable` (503), and the
   client-only `busy`.
10. Migration is three operations: `export`, `import`, `markMigrated`.
11. On the services, presence also lasts 2 minutes after a `renewPresence`;
    on GitHub, 60 minutes after the last renewal.
12. The runtime record carries `backend` and `repositories` (the
    misconfiguration check) and `status` (the state behind the notifications).
13. Infrastructure resources are declared with the units and edited through
    `setUnits`.
14. The endpoint record is the full one (`url`, `scope`, `protocol`, `auth`,
    `meta`), with `url` as the endpoint's address.
15. The misconfiguration check's findings come back as `warnings` in the local
    service's `listRuntimes` answer.
