# Panels, views and sidebars

Where the extension shows itself in VS Code: the bottom panels, the sidebars and their views, which handler or service each belongs to, and how roles, aspect guidelines and a workspace without a quest show up there. The user-facing description of each feature is in `doc/user_guide.md`; the modules are in `architecture.md` § Module catalogue.

## 1. The bottom panels

- Bottom panel **@CHAT** — `tomAi.chatPanel` webview with two chat subpanels, **ANTHROPIC/LLM** (section id `anthropic`; config keys, trail subsystem, history file names and tool names keep `anthropic`) and **Copilot**, and the **Logs** section (described below with the @WS Documentation viewer it shares its engine with). A local model runs through an Anthropic profile whose configuration is a Local LLM configuration. Both subpanels' tools button opens **Extension Tools**: an open button for every editor and page, from the same catalogue (`src/utils/extensionToolsCatalog.ts`) as the Status Page's **Editors and pages** overview at its top.
- Bottom panel **@WS** — `tomAi.wsPanel` (workspace), six accordion sections: **Guidelines**, **Documentation**, **Settings**, **Issues**, **Tests**, **Quest TODO**. The @CHAT **Logs** section and the quest-document sub-tabs of **Documentation** are read-only viewers sharing one engine (`questLogs-handler.ts` + `media/questLogs/`, the client a factory with one viewer per section; each panel hosts its own). **Logs** shows one Anthropic session's files — MD Trail and Trail (its `live-trail.md`, rendered and as source), Prompts, Answers, Current Prompt — from `history/sessions/<session>/`, with a **session switch** above the tabs: one button per session, most recently used first, and with more than four a dropdown of every session before the four most recent (the plan is `src/utils/sessionSwitch.ts`, computed by the host on every poll, so it follows sessions created and deleted; the chosen session is one for every Logs tab, kept in the webview state); the session's actions — raw trail, trail summary, history, live trail, memory, clear history — sit behind the switch. **Documentation** has sub-tabs: **Documents** (the group/file editor) and the quest's own documents — Quest Progress, Quest Overview, Quest Notes, Quest Refresh, DocUpdate, Deferred, Questions, Decisions. Three of those are journals the assistant appends to: `deferred.<quest>.md` (deferred steps), `questions.<quest>.md` (every `askUser` / `askUserPicker` question, every Agent SDK `AskUserQuestion` the transport intercepts, and the answer given), `decisions.<quest>.md` (the `decisions[]` of each archived todo, with its id and archive time). Each tab reads a 256 KB window from the end its newest content is at — the tail for the appended-to files (the live trail and the three journals), the head for the rest — and opens scrolled to that end. A tab names an **area** as well as a file (`questLogLocation` → `{area, fileName}`): the quest documents read the quest folder, the Logs tabs its `history/` subfolder (`sessions/<session>/…`). Current Prompt has a dropdown — six variants, `{Chat, Queue} × {Literal, User, System}` — so the change-detection cache is keyed by `questLogViewKey` (tab + variant + session).

## 2. The @TOM and @TOM WS sidebars and the PROCESS view

- Sidebar **@TOM** (`tomAi-sidebar`, the quest) — **PROCESS** (process, phase, step, sub-step, iterations), QUEST NOTES, QUEST TODOS (with @WS › Quest TODO a todo manager across quests: a quest scope — one quest, the open windows' quests, or all with checkboxes — live / archived / deleted toggles with Restore, ordering by quest, a quest prefix; `utils/todoPanelScope.ts`), **SESSIONS** (the quest's named sessions plus `default` / `chat`, with base, lifetime, profile and model; add, reset, delete, remove the unused ones in one step — `sessionsView-handler.ts`), SESSION TODOS. Sidebar **@TOM WS** (`tomAi-ws-sidebar`, the workspace) — VS CODE NOTES, WORKSPACE NOTES, WORKSPACE TODOS, TODO LOG, WINDOW STATUS. The PROCESS view's action bar offers the moves of the current position: **Proceed** runs it — the action page (custom instructions, session, preview) queues its prompt, which runs as that position, and a process-move marker after it (`src/utils/processMoveMarker.ts`); what the prompt queues goes in before the marker, and the state moves on when the queue reaches the marker with all of it done (meanwhile the view shows ⏳ running — N items left; a failed item holds the marker, and Proceed offers to repeat the step or move on) — after a decision point (a gate, a phase's end, a repeatable level) to the decision after it, where **Decide…** asks the user to go on, repeat or (after a gate) pass / fail it, a failed gate going to the gate's `onFail` step or back to the start of the current or the previous phase; Skip, Back and **Back to the start of the current / previous phase** (that phase's first step, the iterations counted on) only move. A step or sub-step marked `userAction: true` is the user's: the view shows a *Your turn* box, and Proceed asks the user to confirm it is done instead of queuing a prompt. A review step or sub-step may name the documents under review (`documents:`, a path with an optional label); the view links them at that step. A phase may name the phases that follow it (`next:`, conditions; `[]` ends the process), so a process may branch and meet again; a `goto:` step passes the other alternative; the view shows the flow and the path taken. A step may be a **decision step** (`decision:`): when the step before it has finished it chooses where the process goes — any step or phase, automatically from chat variables, by the user at Decide…, or judged by the agent (`tomAi_setProcessState {decide}`) — the jump recorded (`jumps`) with the iterations counted on. A phase or step may be `optional` and carry `when:` — a chat-variable test the extension decides, or a `judge:` text the agent decides at Proceed; **Leave out** passes it, and the view lists what was left out (the state's `skipped`). The process template editor (`tomAi.editor.processTemplates`) edits the Proceed template. A step may list `subprocesses:` (hand outputs back) and `branches:` (hand nothing back); a started one is a level on the quest's process stack (`process-state.<quest>.yaml`), started and aborted from the PROCESS view's title bar or the **process branching editor**, and suggested by an agent with `tomAi_suggestSubprocess`. Sessions: a sub-step, step, phase or the process itself may name the session its prompts run in (`{name, basedOn, mode, profile}`, the innermost applying); the process editor picks them with the session picker (definition only — Proceed creates a missing session with its profile) and refuses a profile the window does not have. The process editor opens from the hierarchy button at the bottom of every @CHAT subpanel; processes live in `_ai/processes/<id>/` (`<id>.process.yaml` + `<id>.md`), a quest's position in `process-state.<quest>.yaml` in its folder. A quest may hold several positions, *runs* (`process-state.<quest>.<run>.yaml`, any process; the quest's own file is the run `default`, which runs no process); a window works on one run at a time, which the PROCESS view (its **Runs** list: select, +, trash, and **Reset Process** / **Reset Run** — back to the process's start clearing the declared `runParameters`, or everything process-related), the process chat variables and the process tools follow (`tomAi_*ProcessRun*`); a run other than `default` has its own custom chat variables and its own sessions (`<session>@<run>`); every run has its default session `default@<run>` (`default@default` for the default run; an older build's bare `default` is renamed at a window's start), created with the run based on `default@default` — the queue's session for the run's items that name none. Every queue item carries its run (badge; the Prompt Queue editor has a tab per run, each that run's queue with its own toolbar and defaults); each run has its own lane (the lanes send in parallel) and its own queue settings — auto-send (Pause / Resume), Auto-Start / -Pause / -Continue, the defaults, the Copilot answer timeout and reminder (`queue-settings.yaml` `runs:`). A sending item whose turn waits (`tomAi_waitFor`, its background work) has a **Message** box in its wait panel that writes to its own turn (the agent reads it and waits on), and one whose turn asks shows an ask panel answered in place (`services/queueItemAsks.ts`). A queue item's done notification is queued in its own run, or in another run or another quest's queue (through that quest's inbox) when the item names one (`doneNotificationRun` / `doneNotificationQuest`). Each @CHAT chat subpanel shows its **Session** and **Run** as fields, label above and value a link below (VS Code pickers; the other choices of its action bar — Model, Template, Role, the reusable prompt's type, scope and file — are fields of the same kind, each select hidden behind its field, `linkChatSelects` in `media/chatPanel/main.js`, the host's `pickFromSelect`): what it shows, sends and queues with the panel's target follows that run, and switching it selects **Run default** — the run's default session (ANTHROPIC/LLM). Run default is a choice of the chat and todo panels' profile, session, template and role pickers: an item queued with it carries no setting of its own and takes its run's when it is sent (`utils/runDefaultChoice.ts`). Save to Queue and Queue next always queue into the default run with the queue's settings (`default@default`); the buttons after the session and run use the panel's own (Send, Save to Queue / Queue next with the panel's session and run). The todo panels have the same pair: a default queue button and the queue-target flow. A process, phase or step may name **follow-up processes**: the decision at its end offers to continue in one of them at a named position.

## 3. The @TOM VSC, @TOM TODO and @TOM INFO sidebars

- Sidebar **@TOM VSC** (`tomAi-vsc-sidebar`, this VS Code window) — **RESOURCES** (`tomAi.vscResources`): the window's extension helper processes grouped by extension (memory, CPU; pause / resume / kill), Lean / Full profiles, toggles for the heavy workspace settings; a status-bar item shows their total memory and opens it. **PREREQUISITES** (`tomAi.prerequisites`, `prerequisitesView-handler.ts`): every project's (and repository root's) `prerequisites.yaml` — the secrets it needs with the ways to provide them, never a value, and the software it expects (format: `_agent_guidelines/prerequisites_yaml.md`, schema `src/config/prerequisites.schema.json`) — as a tree repository → project → section → secret / tool → option with ✓ / ✗ / ? roll-ups; checks (presence only; env and tools in VS Code and in a login shell) run on Check now / Refresh, their results, time, open nodes and filters in global storage so every window shows the last check; Create for a project without a file.
- Sidebar **@TOM TODO** (`tomAi-todo-sidebar`) — one view, **TODO** (`tomAi.tomTodo`): the todo panel on its own, a panel instance of its own that starts on the workspace's quests with the quest prefix on. **AI workspaces:** `_ai/workspaces/<workspace>.yaml` (`<workspace>` the window's root folder) lists a workspace's quests (AI Workspace Quests editor, `tomAi.editor.aiWorkspaceQuests`); the quest choosers offer them first with an escape to every quest, and `tomAi_listQuests` answers them by default.
- Sidebar **@TOM INFO** (`tomAi-info-sidebar`, the quest notes on their own, the runs, the user notifications, the notifications) — **QUEST NOTES — `<quest>`** (`tomAi.questNotesPanel`, `questNotesPanel-handler.ts`), on the same `quest-notes.<quest>.md` as the @TOM view: an **Edit** tab (a text area, saved on a short debounce and on blur; a change on disk is taken in unless there is unsaved text, then it asks) and a **View** tab (the MD Browser's own renderer, read-only: folding, search, links), and a button that opens the file in an editor. **RUNS** (`tomAi.runsOverview`, `runsOverview-handler.ts`): every process run of every window on this machine, grouped by window, with its subject, process › position and state — waiting for user > waiting for event > waiting on task > running > paused > idle, with what it waits for (`src/utils/runActivity.ts`); each window writes its runs into its window-state file with its heartbeat, and `tomAi_getQuestWindowStatus` answers them (`runs`). **USER NOTIFICATIONS** (`tomAi.userNotifications`, `userNotifications-handler.ts`): everything directed at the user from every window — asks (open with how long, until answered), tomAi_notifyUser messages, suggested subprocesses, process decisions waiting, todos for the user, the queue holding — one row each from the same log; a todo waiting for decisions is a row from any window's todo events, open until decided; **Answer** opens an ask where it waits — another window's as a stand-in in this window's user-input panel, answered back to that window (`services/windowRequests.ts`, `services/remoteAsks.ts`) — or a decision's todo in @WS › Quest TODO, and **Continue queue** resumes the run a decided todo held; Dismiss hides a row there only; the badge counts open asks and waiting decisions. An answer an agent gave without waiting (`tomAi_answerUser`: title, Markdown answer, suggested prompts and complete suggested todos) is a row there too and opens in the **Answers** page (`@T: Answers`, `tomAi.showAnswers`, `answersPanel-handler.ts`): list left, answer right, **Add todo** per suggested todo, **Copy** per suggested prompt; the answers are stored per real `_ai` folder in global storage (`utils/userAnswers.ts`), outside git, until deleted. **NOTIFICATIONS** (`tomAi.notifications`, `notifications-handler.ts`): queue and todo events (item queued / deleted, todo created / edited / status changed) of every window on this machine from one log in the extension's global storage (`services/notificationLog.ts`, the last 1000), merged per type, source and quest within 60 s, filterable by window and type, details on hover or click.

## 4. Roles, role types and aspect guidelines

- **Roles and role types.** A role is `_ai/roles/<role>/` (`role.md`, and `role-config.yaml` naming its type); a role type is `_ai/role-types/<type>/role-type.yaml`. A prompt runs with the tools of the role it runs as — the first that names one of the todo's `role`, the queue item's, the process step's, the run's default role, the chat variable `role` (`utils/promptRole.ts`): the type keeps the profile's tools or replaces them with a selection; a fixed always-on set stays. Edited in the one Role Editor (Roles and Role Types tabs); schemas in `.tom/json-schema/roles/`. **Aspect guidelines** (the guideline selector; `_ai/aspect_guidelines/<aspect>/`: `aspect.yaml` and one `<choice>.md` per choice, or a guideline file `_agent_guidelines/aspects/<aspect>/<choice>.md` of the root or a workspace folder, the nearest winning) get one choice per aspect and level — the aspect's default < workspace (`workspace_aspects.md` / `.yaml` of the root and the workspace folders) < quest default < window < run < role type < role < item < todo, `remove` sending nothing — and sent under `## Aspect guidelines`; the shared guideline picker (`media/shared/aspectPicker.js`) sets them in the Prompt Queue editor, the run's info line, queue items, todos, @CHAT and the Role Editor, the Aspect Guidelines editor (`tomAi.editor.aspectSections`) edits the aspects; agents set the item and todo levels with the tools' `guidelines` (`tomAi_getAspectGuidelines` reads them), and the Proceed template tells them to name `role` and `guidelines` on the secondary work they queue.

## 5. No quest open, a new workspace

- **No quest open / new workspace.** In a folder without `.tom/` the panels are placeholders offering **Setup new workspace folder** (`tomAi.setupWorkspaceFolder`: unpacks `resources/workspace_template.zip`, the configuration, guidelines and `_ai` roles / processes / schemas / prompts plus the starting quest `tomai_introduction`, asking per existing file). While a set-up workspace has no quest open (`default`), @CHAT, @WS and the @TOM quest views show a *No quest is open* banner with that button and **Create new quest** (`tomAi.createQuest`: a quest's files and its `questsetup1` todo, which defines the quest with the user). A quest window opens its overview in the MD Browser once per quest and machine.
